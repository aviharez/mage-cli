Executes a given bash command in a persistent shell session with optional timeout, ensuring proper handling and security measures.

Be aware: OS: ${os}, Shell: ${shell}

All commands run in the current working directory by default. Use the `workdir` parameter if you need to run a command in a different directory. AVOID using `cd <directory> && <command>` patterns - use `workdir` instead.

IMPORTANT: This tool is for terminal operations like git, npm, docker, etc. DO NOT use it for file operations (reading, writing, editing, searching, finding files) - use the specialized tools for this instead.

Before executing:
- If the command will create new directories or files, first use `ls` to verify the parent directory exists and is the correct location.
- Quote file paths that contain spaces with double quotes (e.g., `mkdir "/Users/name/My Documents"`, not `mkdir /Users/name/My Documents`).

Usage notes:
  - The command argument is required.
  - Optional timeout in milliseconds; defaults to 120000ms (2 minutes).
  - Write a clear, concise description of what the command does in 5-10 words.
  - If output exceeds ${maxLines} lines or ${maxBytes} bytes, it is truncated and the full output is written to a file; use Read (offset/limit) or Grep on that file. Do NOT use `head`/`tail`/other truncation commands to limit output - it's already captured in full.
  - Avoid `find`, `grep`, `cat`, `head`, `tail`, `sed`, `awk`, `echo` unless truly necessary; prefer: Glob (file search), Grep (content search), Read (view files), Edit (modify files), Write (create files), plain text output (communication).
  - When issuing multiple commands: if independent, send them as multiple Bash tool calls in a single message to run in parallel. ${chaining} Use ';' only for sequential commands where earlier failures don't matter. Do NOT use newlines to separate commands.
  - AVOID `cd <directory> && <command>`; use `workdir="<directory>"` instead.

# Git commits and PRs
Only commit or push when the user explicitly asks. Never force-push to main/master without explicit confirmation, skip hooks, or use `git rebase -i`/`git add -i` (no interactive input support). Never update git config.

Avoid `git commit --amend`. Only use it when ALL of these hold:
  1. The user explicitly requested amend, OR the commit succeeded but a pre-commit hook auto-modified files that need including.
  2. HEAD was created by you in this conversation - verify with `git log -1 --format='%an %ae'`.
  3. It has not been pushed - verify `git status` shows "ahead" of the remote.
If a commit FAILED or was REJECTED by a hook, never amend - fix the issue and create a new commit. If it's already been pushed, never amend unless the user explicitly asks (it requires a force push).

To commit: gather `git status`, `git diff`, and recent `git log` (in parallel), draft a concise why-focused message, stage only the relevant files, then commit and verify with `git status`.

To open a PR: use `gh`. Gather status/diff/upstream-tracking state and the full commit history since diverging from the base branch (in parallel), then push (with -u if needed) and `gh pr create` with a HEREDOC body containing a Summary section. Return the PR URL when done.
